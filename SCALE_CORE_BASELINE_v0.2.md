# 1. Executive Summary

이번 Consolidation의 핵심 결론은 다음과 같다.

1. **현재 Scale Layer는 Solo에서는 Canonical Core를 운영할 수 있고, Micro에서는 Routing은 가능하지만 Core는 Candidate 수준이며, Small / Mid+는 Routing-only Evidence Boundary 상태다.**

2. 기존 상태는 변경하지 않는다.
   - `SC-SOLO-001` — PROVISIONAL CORE — VERY HIGH
   - `SC-SOLO-002` — PROVISIONAL CORE — Canonical Confidence not separately scored; Integration Assessment VERY HIGH
   - `SC-SOLO-003` — PROVISIONAL CORE
   - `SC-SOLO-004` — PROVISIONAL CORE
   - `SC-MICRO-001` — KEEP AS CANDIDATE — LOW-MEDIUM
   - Small / Mid+ — NO PROMOTED SCALE CORE

3. **`SC-SOLO-002 — Visible Scope ≠ Production Scope`가 51개 Genre Scale Handoff를 받는 가장 강한 Parent Scale Rule이다.**
   - 51개 Handoff 중 canonical Risk Tag 기준 `QA`가 **32개**, `Content`가 **21개**, `Logic`이 **17개**, `Technical`이 **13개**에 등장한다.
   - 이는 화면 수 / 플레이타임보다 Interaction Matrix, authored content, logic dependency, technical state가 실제 Scope Driver임을 반복적으로 지지한다.

4. **`SC-SOLO-003 — Common Grammar is a Content Multiplier`도 유지 / 강화 가능하다.**
   - Layer 3의 Luck be a Landlord, SNKRX, Brotato 같은 사례는 공통 Grammar / Data 확장이 자산·코드 비용을 낮출 수 있음을 지지한다.
   - 동시에 Deck / Roguelike / Simulation Handoff는 Balance / Tooltip / Regression / Edge-case QA가 사라지지 않음을 반복적으로 보여준다.
   - 따라서 Reuse는 `Free Content`가 아니라 **Cost Shape를 Unique Production에서 Reusable + QA-heavy Production으로 바꾸는 Mechanism**으로 본다.

5. `SC-SOLO-001 — Risk-first Prototype`은 Solo에서 매우 강하지만 Layer Ownership은 Solo 전용이라고 보기 어렵다.
   - Buckshot Roulette / Thronefall / Jam-to-product 사례가 Solo/Micro에서 강하게 지지한다.
   - 그러나 위험한 Design Claim을 먼저 검증해야 한다는 원칙은 큰 팀에도 적용 가능하다.
   - **결론:** Canonical SC 상태는 유지하되 `Universal Validation Parent Candidate / Solo Amplification` 관계를 기록한다. 이번 단계에서 Reclassify하지 않는다.

6. `SC-SOLO-004 — Never Copy Post-success Scope` 역시 유효하지만 General Production / Reference Analysis 원칙일 가능성이 높다.
   - **결론:** Canonical SC 상태 유지 + `Reference Analysis Parent Reclassification Candidate`로 기록한다.

7. `SC-MICRO-001`은 여전히 Candidate가 맞다.
   - Layer 3에는 2인, 4인, 협업 사례가 존재해 **역할 전문화와 병렬화가 Solo와 다른 Mechanism**임을 정성적으로 보여준다.
   - 그러나 `2명 vs 3명 vs 5명`의 Scope cut line, throughput, coordination cost를 정량 비교할 Evidence는 없다.

8. Solo와 Micro 사이에서 가장 먼저 달라지는 것은 `Content Quantity` 자체가 아니라 **Parallel Production Capacity / Specialist Coverage / Review Ownership**이다.
   - Micro는 Code + Art, Design + Implementation 등을 병렬화할 수 있다.
   - 그러나 headcount 증가를 `Scope × N`으로 환산하지 않는다. Integration / review / communication cost가 추가된다.

9. 51개 Handoff는 **새 GSC가 아니다.**
   - 이번 문서는 각 Handoff를 Cost Shape / Scale Sensitivity / Externalization / Internal Ownership / Tooling / QA 관점으로 Normalize한다.
   - 이 정보는 완료된 `Genre × Scale Integration`의 입력으로 사용되었으며, 향후 신규 Evidence에 따른 재통합 시에도 동일 Routing Data로 사용한다.

10. 51개 중 가장 반복되는 Risk Cluster는 **QA / Interaction**이다.
    - `QA` 태그가 32 / 51 Handoff에 등장한다.
    - 그 다음은 `Content` 21, `Logic` 17, `Technical` 13, `UI` 9, `Balance` 8 순이다.
    - 따라서 Solo/Micro Scope Review에서 **content count보다 regression / combination / state coverage를 먼저 보는 프로젝트가 많다.**

11. Outsourcing은 Cost를 제거하지 않고 자주 다음으로 이동시킨다.

```text
Internal Production
→ Specification
+ Vendor Communication
+ Revision
+ Integration
+ QA
```

12. AI-assisted Production도 `Headcount +1`이 아니다.
    - Draft / boilerplate / variation / documentation / search cost를 줄일 수 있다.
    - Ownership / integration / final QA / design judgment는 별도다.
    - Scale Router에서는 `PRODUCTIVITY_MODIFIER`로만 기록한다.

13. 기존 세 GSC는 `Genre × Scale Integration` 결과 모두 `RETIRED_AS_INDEPENDENT_GSC`로 Canonical Sync되었다.
    - Deck-Solo → Parent + Handoff
    - Mgmt-Solo → Parent + Handoff + Routing Specialization
    - Deduct-Solo → Parent + Handoff

14. `Genre × Scale Integration / Canonical GSC Sync`는 완료되었다.
    - 현재 `Active Independent GSC = 0`.
    - 다음 단계는 `Universal Core Consolidation`이다.
    - Small / Mid+는 여전히 `EVIDENCE_BOUNDARY_SCALE`로 유지한다.

# 2. Scale Layer Purpose

Scale Layer의 질문은:

> **“이 설계가 좋은가?”**

가 아니라:

> **“이 설계를 현재 Production Ownership / Parallel Capacity / Specialist Coverage에서 현실적으로 만들고, 반복 검증하고, 유지할 수 있는가?”**

다.

따라서:

```text
Great Design
≠
Solo Viable
```

```text
High Production Cost
≠
Bad Design
```

Scale는 `Production Viability` Layer다.

Design Quality 점수와 분리한다.

# 10. Cost Shape Classification

Cost Shape는 Core가 아니라 Risk Routing Aid다.

## LINEAR

Content 1개 추가 시 비용이 비교적 일정하게 증가.

## SUBLINEAR / REUSABLE

공통 Grammar / tooling으로 추가 단위의 제작비가 낮아짐.

## MULTIPLICATIVE

```text
A × B × C
```

조합 때문에 QA / logic / balance 비용 증가.

## THRESHOLD

특정 규모를 넘을 때:
- tool
- architecture
- specialist
가 새로 필요.

## SPECIALIST-GATED

특정 전문 역량 없이는 throughput / quality가 급격히 제한.

## ITERATION-HEAVY

초기 구현보다 반복 tuning / polish / revision이 주요 비용.

## UNKNOWN

현재 Source로 Cost Shape를 안정적으로 판정하기 어려움.

### Multiple Shape

한 Handoff는 여러 Shape를 가질 수 있다.

예:

```text
Action VFX
= Linear asset cost
+ Specialist-gated
+ Iteration-heavy
```

# 11. Common Grammar Audit

Project Content Unit을 다음으로 분류한다.

| Content Unit Type | Logic Cost | Asset Cost | QA Risk | Typical Solo Value |
|---|---:|---:|---:|---|
| Data-only | Low initial | Low | Medium~High as combinations grow | High |
| Data + Asset | Low logic | Medium | Medium | Medium-High |
| Shared Logic Variant | Medium | Variable | Medium-High | Medium |
| Unique Logic | High | Variable | High | Low unless core value |
| Unique Presentation | Variable | High | Medium-High | Low unless hook / promise |

## Audit Questions

1. 신규 콘텐츠의 대부분이 어느 유형인가?
2. Data-only라도 Tooltip / Balance / Regression이 증가하는가?
3. Shared Grammar가 Player에게 반복으로 느껴지는가?
4. Unique Logic이 Core Experience에 직접 필요한가?
5. Tooling이 추가 콘텐츠 비용을 실제로 줄이는가?

`Common Grammar Ratio`는 Formal Definition 없이는 일반 Metric으로 사용하지 않는다.

# 14. Solo Scale Findings

Solo에서 Production Risk가 증폭되는 주요 Mechanism:

## 14.1 Single Ownership

한 Domain에서 Block되면 전체 Project flow가 멈출 수 있다.

## 14.2 Context Switching

Code → Art → UI → QA 전환 자체가 throughput cost.

## 14.3 No Parallel Capacity

핵심 기능 구현 중:
- content
- art
- polish

# 22. Conflicting Findings

## 22.1 Reuse vs Variety

Reuse:
- code / asset cost ↓

Risk:
- repetition
- balance
- regression
- tooltip burden ↑

Resolution:
Reuse ratio와 Player-perceived variety를 별도 Layer에서 본다.

## 22.2 Tooling Cost vs Tooling ROI

Long / repeated content pipeline:
- tooling value ↑

Short prototype:
- tooling opportunity cost ↑

Threshold는 프로젝트별로 검증한다.

## 22.3 Outsourcing vs Integration

External production throughput ↑ 가능.

하지만:
- specification
- revision
- integration
- acceptance
가 새 internal lane을 차지한다.

## 22.4 Specialization vs Coordination

Micro specialization은 parallelism을 늘릴 수 있다.

동시에:
- dependency
- review
- communication
비용을 만든다.

## 22.5 Content Count vs Interaction Complexity

콘텐츠 수가 적어도:

```text
few objects
× many states
× many sequences
```

면 QA Scope가 클 수 있다.

## 22.6 Polish vs Breadth

적은 content + 높은 polish와
넓은 content + 낮은 polish는 다른 Cost Shape다.

Design Quality가 아닌 Product Promise / Production choice로 본다.
